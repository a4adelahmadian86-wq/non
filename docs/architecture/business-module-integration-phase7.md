# مرحله هفتم: ممیزی و قرارداد یکپارچگی ماژول‌های کسب‌وکار

تاریخ ممیزی: 2026-11-11

## هدف و مرز این سند

این سند خروجی ممیزی اولیه مبتنی بر کد `main` و قراردادهای لازم برای ادامه مرحله هفتم است. این سند ادعای تکمیل مرحله هفتم یا تأیید سلامت runtime نیست. هیچ Migration، داده عملیاتی، سرویس production یا شاخه همکار در این تغییر مستقیماً دست‌کاری نشده است.

قاعده ادغام: قابلیت‌های پیشنهادی در PRهای باز، تا زمان ادغام و عبور از CI، بخشی از `main` محسوب نمی‌شوند.

## 2. شواهد مستقیم از کد main

- `routes/web.php` مسیرهای اصلی را به فایل‌های دامنه‌ای store، support، notifications، messenger و product operations واگذار می‌کند.
- `StoreProduct` رابطه‌های محصول با فایل‌ها، پیش‌نمایش، تصاویر، دوره، کتابخانه و اقلام سفارش را تعریف می‌کند.
- `StoreOrderItem` هم به `Order` و هم به `StoreProduct` متصل است و snapshot عنوان، SKU، قیمت، مالیات، تخفیف و مشخصات محصول را نگه می‌دارد.
- checkout در `StoreCartController` محصولات را مجدداً از کاتالوگ بارگذاری می‌کند، قابلیت خرید و آمادگی فایل/دوره را می‌سنجد و شناسه فایل و SHA-256 را در snapshot قلم سفارش ثبت می‌کند.
- `Payment` به `Order` متصل است؛ `Order` رابطه اقلام فروشگاه و پرداخت‌ها را دارد.
- `StoreCourseEnrollmentService` ثبت‌نام را از `StoreLibraryItem` و `StoreProduct` می‌سازد.
- `SupportTicketService` چرخه ساخت تیکت و پیام را مدیریت می‌کند و برای پیوست از StorageManager استفاده می‌کند.
- `NotificationService` درگاه واحد ثبت/خواندن اعلان است و dedupeKey را پشتیبانی می‌کند، اما اجباری نیست.
- `Conversation` پیام‌ها و اعضا را نگه می‌دارد و scope عضویت در `MessengerAccessService` کنترل می‌شود.
- `FarastDocument` و `TypingDocument` دو مدل جدا با پیوند صریح هستند؛ نباید بدون مهاجرت/قرارداد، یکی را جایگزین دیگری کرد.

## 3. موانع پیش‌نیاز که اجازه ادغام کامل نمی‌دهند

این موارد در `main` یا وضعیت PRها به‌عنوان گیت باقی‌مانده دیده شدند؛ تا حل آن‌ها اتصال سراسری عملیات حساس مجاز نیست:

1. **هسته دسترسی و اتوماسیون:** `AuthorizationService.php` موجود در main هنوز نسخه ساده role/permission است. PR #330 نسخه scoped RBAC و Workflow/Outbox را پیشنهاد می‌کند و نباید بدون CI و حل هم‌پوشانی/تعارض وارد main شود.
2. **یکپارچگی مالی و idempotency:** PR #340 کلیدهای idempotency، قیود ارجاعی و آزمون migration ارتقایافته را پیشنهاد می‌کند. تا قبل از تعیین تکلیف، checkout و callback و wallet top-up را نباید یکپارچه‌شده نهایی اعلام کرد.
3. **چرخه ورود و انتشار محصول:** PR #333 مسیر type-first intake و بررسی/انتشار را تغییر می‌دهد و فایل‌های `StoreProduct`، `AdminStoreController`، `AuthorizationService` و routeها را لمس می‌کند. این PR باید با PRهای امنیت و ذخیره‌سازی بدون بازنویسی کار همکاران همگام شود.
4. **چرخه عمر فایل محصول:** PR #335 انتقال/حذف/رزرو ظرفیت فایل محصول را روی StorageManager موجود تقویت می‌کند.
5. **سیاست ذخیره‌سازی و backup:** PR #343 موارد invalid classification و صف backup را اصلاح می‌کند. در نسخه فعلی StorageManager، classification ناشناخته به non_critical تبدیل می‌شود؛ این رفتار تا اصلاح باید مانع تأیید مسیرهای فایل حساس تلقی شود.
6. **تست‌های پایه و Reader:** PRهای #344 و #346 برای اصلاح شکست‌های Reader باز هستند؛ CI کامل باید روی HEADهای نهایی بررسی شود.

وجود این PRها به‌تنهایی وضعیت سبز، ادغام‌شده یا deploy-ready را اثبات نمی‌کند.

## 4. قراردادهای یکپارچگی که باید به آزمون سرتاسری تبدیل شوند

### A. محصول تا تحویل دیجیتال
1. محصول فقط از `StoreProduct` کاتالوگ انتخاب شود.
2. checkout فقط محصول منتشرشده و قابل خرید را بپذیرد.
3. سفارش یک `StoreOrderItem` با `product_id` معتبر و snapshot غیرقابل‌ابهام بسازد.
4. برای فایل دیجیتال، `product_file_id` و SHA-256 دقیق همان فایل در snapshot تثبیت شود.
5. پرداخت موفق فقط همان سفارش را تسویه کند.
6. اعطای کتابخانه فقط از سفارش پرداخت‌شده و همان قلم سفارش انجام شود.
7. دانلود باید entitlement، مالکیت و همان فایل pinned را بررسی کند؛ نه فایل جدیدی که بعداً جایگزین شده است.

### B. محصول دوره‌ای تا پیشرفت یادگیری
1. دوره باید به همان `StoreProduct` متصل باشد.
2. checkout همان محصول را در `StoreOrderItem` ثبت کند.
3. پس از پرداخت، `StoreLibraryItem` و `StoreCourseEnrollment` به همان product/course/order متصل باشند.
4. هر درخواست درس، منبع و ثبت پیشرفت باید enrollment معتبر و زمان دسترسی را بررسی کند.
5. لغو/بازپرداخت/ابطال دسترسی باید سیاست روشن و قابل ممیزی داشته باشد؛ رفتار فعلی باید قبل از پیاده‌سازی این بخش بررسی شود.

### C. سفارش تا پرداخت و دفتر مالی
1. هر callback با شناسه تلاش/کلید idempotency مشخص شود.
2. مجموع پرداخت‌های موفق، مبلغ سفارش و وضعیت سفارش باید قابل تطبیق باشد.
3. هر debit/credit کیف پول باید یک تراکنش دفترکل متناظر داشته باشد.
4. هیچ retry یا callback تکراری نباید پرداخت، برداشت یا اعطای دسترسی را تکرار کند.
5. اصلاح یا برگشت مالی باید با تراکنش جبرانی ثبت شود؛ حذف یا بازنویسی تاریخچه مالی مجاز نیست.

### D. مشتری و پشتیبانی
1. شناسه مشتری در تمام سفارش‌ها، پرداخت‌ها، کیف پول، کتابخانه و تیکت‌ها به `User` واحد متصل باشد.
2. تیکت مرتبط با محصول باید `related_product_id` معتبر داشته باشد.
3. دسترسی کارشناس و مدیر به مشتری/تیکت باید در محدوده RBAC نهایی enforce شود.
4. پیوست پیام تیکت باید managed-file reference معتبر و قابل بازیابی داشته باشد.
5. تغییر وضعیت، پاسخ و ارجاع باید رویداد دامنه‌ای واحد تولید کند.

### E. پیام‌رسان و اعلان
1. هر مکالمه فقط برای اعضای مجاز قابل مشاهده باشد.
2. پیوست پیام باید مالکیت، checksum، مرجع Storage و کنترل دانلود داشته باشد.
3. رویداد دامنه‌ای فقط یک اعلان منطقی با dedupe key پایدار بسازد.
4. وضعیت اعلان از نتیجه واقعی عملیات استخراج شود؛ اعلان منبع حقیقت وضعیت سفارش یا پرداخت نیست.
5. شکست تحویل اعلان نباید تراکنش مالی/تجاری را به‌صورت مبهم rollback یا موفق جلوه دهد.

### F. پروژه و اسناد
1. مالک پروژه و سند در تمام عملیات حفظ شود.
2. پیوند `FarastDocument` و `TypingDocument` یکتا و سازگار بماند.
3. نسخه‌ها و بازیابی سند باید history را حفظ کنند.
4. فایل‌های سند از StorageManager عبور کنند و ارجاع‌ها با مالک/نوع منبع تطبیق داده شوند.
5. CRM و گزارش‌ها نباید شمارش اسناد دو مدل را دوباره‌شماری کنند.

## 6. معیار پذیرش مرحله هفتم

مرحله فقط وقتی قابل بستن است که شواهد CI و آزمون سرتاسری موارد زیر را ثابت کنند:

- سفارش به محصول و فایل/دوره دقیق متصل است؛ snapshot تاریخی قابل تغییر ناخواسته نیست.
- پرداخت و کیف پول قابل تطبیق‌اند و عملیات تکراری اثر مالی تکراری ندارند.
- تحویل فایل و پیوست فقط از StorageManager و entitlement معتبر عبور می‌کند.
- ثبت‌نام و پیشرفت دوره به همان محصول و سفارش قابل ردیابی است.
- CRM، تیکت، پیام‌رسان و اعلان از شناسه‌ها و وضعیت‌های منبع حقیقت استفاده می‌کنند.
- دسترسی بین کاربران/سازمان‌ها در تمام endpointها و jobها رد می‌شود.
- retry، شکست صف و callback تکراری داده متناقض ایجاد نمی‌کند.
- هیچ جدول، سرویس، route یا workflow موازی برای دور زدن زیرساخت موجود ساخته نشده است.

این ممیزی از خواندن فایل‌های مشخص در شاخه main و توضیحات PRهای مرتبط تهیه شده است. اجرای PHP/PHPUnit، مشاهده دیتابیس محلی/تولیدی، اجرای migration، بررسی همه فایل‌های مخزن، و اجرای browser/E2E در این مرحله انجام نشده است. بنابراین این سند نقشه شواهد اولیه و قرارداد ادامه کار است، نه گزارش تأیید نهایی runtime.


## 8. یافته‌های مشخص برای اصلاح در ادامه مرحله

### 8.1 هویت رخداد در اعلان تیکت: اصلاح‌شده در main

یافته اولیه درباره کلید dedupe بیش از حد کلی، دیگر وضعیت فعلی `main` را توصیف نمی‌کند. PR #358 ادغام شده و CI آن برای FARAST CI، Phase 3 Commerce Tests و Phase 4 Agent موفق بوده است. کد فعلی `SupportNotificationService` شناسه `TicketMessage` را برای پاسخ مشتری/کارشناس، شناسه transition را برای بستن تیکت، شناسه assignment را برای ارجاع و cycle/threshold را برای SLA وارد کلید dedupe می‌کند. `SupportTicketService` نیز شناسه پیام یا transition واقعی را به notifier می‌فرستد.

بنابراین پاسخ‌ها و transitionهای مستقل یک تیکت از هم تفکیک می‌شوند و replay همان رخداد به کلید یکسان می‌رسد. این مورد از فهرست مانع‌های حل‌نشده خارج می‌شود؛ پوشش runtime و رفتار کانال‌های ایمیل/SMS در تست‌های ادغام‌شده #358 نگهداری می‌شود.

### 8.2 سیاست classification در StorageManager: اصلاح‌شده در main

این ریسک با PR #381 اصلاح و ادغام شد. مقدار classification اکنون فقط در صورت برابر بودن دقیق با `critical` یا `non_critical` پذیرفته می‌شود؛ هر مقدار دیگر پیش از انتخاب Volume، نوشتن یا staging با `InvalidArgumentException` رد می‌شود. آزمون Feature ثابت می‌کند هیچ managed-file، volume یا فایل staging برای مقدار نامعتبر ساخته نمی‌شود. هر سه workflow اجباری PR #381 شامل FARAST CI، Phase 3 Commerce Tests و Phase 4 Agent موفق بودند.

این مورد از گیت‌های باز Storage خارج می‌شود.

### 8.3 مسیرهای اعلان تجاری باید از نظر رویداد واحد تطبیق داده شوند

`SupportTicketService` علاوه بر اطلاع‌رسانی پشتیبانی، رویداد `ticket.created` را به WorkflowEngine می‌فرستد. پرداخت سفارش نیز اعلان مستقیم و dispatch رویداد `order.paid` دارد. وجود این دو مسیر لزوماً خطا نیست، اما باید با تست مشخص شود اعلان‌های داخلیِ مستقیم و اکشن‌های Workflow برای یک رخداد، اعلان تکراری ناخواسته نسازند. مرجع وضعیت همچنان Ticket/Order است و Notification فقط projection آن رخداد است.

### 8.4 محدودیت‌های شواهد

این موارد از کد خوانده‌شده استخراج شده‌اند؛ هنوز با اجرای runtime و تست بازتولید نشده‌اند. بنابراین به‌عنوان یافته ممیزی/ریسک ثبت می‌شوند، نه ادعای وقوع قطعی در production.

### 8.6 بازیابی بکاپ: قرارداد موجود در main و آزمون regression

در HEAD فعلی `main`، دو بخش لازم از قبل پیاده‌سازی شده‌اند: تشخیص نبود ورودی دیتابیس با مقایسه صریح `ZipArchive::locateName(...) === false` و بازسازی رکورد `StorageBackupRun` و ظرفیت Volume پس از restore؛ زیرا snapshot دیتابیس پیش از ثبت run و upload مقصد گرفته می‌شود. بنابراین اصلاح production جدیدی برای این مورد لازم نیست و نباید نسخه موازی ساخته شود.

PR #398 فقط آزمون Integration regression را اضافه می‌کند. آزمون ZIP AES-256 می‌سازد که `database/database.sql` اولین ورودی آن است؛ run و آپلود را پس از snapshot ایجاد می‌کند؛ سپس وجود داده قبل از snapshot، حذف داده بعد از snapshot، بازیابی رکورد backup و ثبت صحیح `used_bytes/object_count` را بررسی می‌کند. این آزمون قرارداد فعلی main را تثبیت می‌کند.

### 8.7 هویت رخداد در اعلان پاسخ تیکت
